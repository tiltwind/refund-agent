# 基线报告 —— run `baseline-4`

r1 全量基线，三档 Recall + 两个辅助数 + 两个 LLM 指标。原始数据在
[`result.json`](./result.json)，跑法见 [README](./README.md)。

```
python rag/experiments/rag-ex-1/run_experiment.py --langfuse --judge --concurrency 8 --run-name baseline-4
```

102 条、2940.1s、`error_rate` 0、judge 调用 0 次失败。分数写回 Langfuse dataset run
`retrieval-cases-r1 / baseline-4`，逐条 `trace_id` 落在结果文件里，六步的中间产物（含装配后的
条款全文）在 trace 上，102 条全部导出到 [`traces/`](./traces/README.md)。

耗时里 98% 是 judge：检索六步合计只花了 224s（单条均值 2.2s），其余是每条两次 judge 调用。
judge 开着思考模式 —— 实测一次 Context Relevance 调用输出 21168 token，其中 20963 是思考
token，占 99%（第七节）。

编号跳过 3：那次跑到 25 条时中止（换 judge 端点），没有 run 级的数，dataset run 已删。

被测参数：`refund_policy_chunks` / BGE-M3 / bge-reranker-v2-m3 / `top_k=4` /
`candidate_limit=20` / `rrf_k=20` / `min_score=0.30` / `0.80+0.20` / `budget=3000`。

## 五、这次跑批暴露的三个链路问题

### 5.1 重排后一条都不剩时，`search_policy` 静默返回空列表

4 条用例（R1-006、R1-026、R1-040、R1-074）拿到了 0 条证据，且不报错。R1-074 在 Langfuse 上
`rag.search_policy` 那棵树：

```
rag.recall     candidates[0] = P10#004:03           ← 种子块排第 1
rag.rerank     passed=0, min_score=0.3, dropped=[全部 20 条]
rag.assemble   sections=[]
```

[`milvus.py`](../../retrieving/milvus.py) 对「一条候选都没有」的口径是显式抛异常，理由写得
很清楚：绝不让 Agent 带着一句「未检索到条款」继续往下判定。但「重排后一条都不剩」走的不是
这条路 —— `assemble([])` 返回 `[]`，工具层拿到空列表，Agent 面对零证据，退回的正是凭记忆
答政策那条路。

召回层明明把正确条款排在第 1，`MIN_SCORE = 0.30` 把它连同其余 19 个候选一起砍掉了。这两件事
（阈值偏高、空结果不报错）要分开处理：前者是调参，后者是口径漏洞。

### 5.2 `unanswerable`：链路给不出「无适用条款」这个结论

6 条全部没抛异常，`unanswerable_raised = 0.0`。异常只在候选为空时触发，而召回层对任何 query
都能捞回 20 个候选。但接上 judge 之后看到的实际行为与上一版报告写的不一样：

| 实际发生 | 条数 | 用例 |
|---|---|---|
| 重排全滤，返回空证据 | 5 | R1-098 ~ R1-102 |
| 返回了不相关的条款 | 1 | R1-097，`context_relevance = 0.000` |

上一版写的「问『保价规则』照样返回一堆退货条款」是从 R1-097 一条推广出去的，不成立：`MIN_SCORE`
在这类 query 上多半已经把候选全砍掉了。真正的缺陷因此换了一个位置 —— **不是「硬凑证据」，
而是链路没有能力说出「语料里没有适用条款」**：它返回的空列表，与 5.1 那种「有正确条款却被阈值
误杀」返回的空列表，是同一个值。调用方无从区分，这两件事也就没法分开处理。

Context Relevance 这一侧给出了判据：唯一那条有证据的样本判出 0.000，而正常样本的均值是 0.238。
两条路仍然是原来那两条 —— 给链路加「最高分低于下限即判无适用条款」的显式结论，或者把这类样本的
判据换成 Context Relevance —— 但现在第二条有实测支撑了。

### 5.3 重复正文占 20.6%

96 条里 57 条含重复，最高 R1-053 的 0.75 —— 四分之三的证据正文是同一段拼了两遍。这与
[`ex-1` 的人工评估报告](../../../evals/experiments/ex-1/human-eval-report.md)在 Agent 侧读到的
是同一个缺陷（那边测得 29.3%），成因在装配的分组键 `(parent_seq, parent_id, section_path)`：
同一父块的子块 `section_path` 各不相同，同一个 `parent_id` 被登记多次。

`rag.assemble` 的 span 带条款全文，重复的段落在 trace 里直接读得到，不必再靠指标反推。而
`recall@3` 满分的用例里照样有 0.4 以上的重复率 —— ID 级 Recall 对它完全无感，这正是当初把
辅助数一起记下来的理由。

**Context Relevance 也抓不到它**：重复率 ≥ 0.4 的 18 条，`CRel` 均值 0.326，比无重复的 35 条
（0.245）还高。原因不难想 —— 被拼两遍的正是命中的那一小节，两份拷贝都判「相关」，重复反而把
相关句的占比抬上去了。所以 `duplicate_ratio` 这个纯函数辅助数不能被 `CRel` 取代，两个测的
根本不是一件事。R1-046 的 [trace](./traces/R1-046.md) 里 judge 列出的不相关句子中，
「下列商品不适用七日无理由退货规定：」原样出现了三次，那就是重复正文在判定侧的样子。

## 六、门禁前要解决的一件事：链路不是确定性的

同一套参数跑了五次（两次离线、三次 dataset run），三档各抖一到两条：

| run | `recall@1` | `recall@3` | `recall@10` | `duplicate_ratio` | `evidence_tokens` | 耗时 |
|---|---|---|---|---|---|---|
| 离线 1 | —（口径修正前） | 0.750 | 0.896 | 0.212 | 1260.9 | 75.2s |
| 离线 2 | 0.637 | 0.750 | 0.896 | 0.208 | 1251.3 | 75.6s |
| `baseline-1` | 0.637 | 0.750 | 0.875 | 0.212 | 1261.4 | 218.2s |
| `baseline-2` | 0.637 | 0.760 | 0.885 | 0.207 | 1267.0 | 206.3s |
| `baseline-4` | 0.625 | 0.760 | 0.885 | 0.206 | 1229.1 | 2940.1s |

翻转集中在 R1-006、R1-021、R1-023、R1-048、R1-064、R1-080、R1-086 这几条 —— 种子块在候选里
本来就排 11~17 名，来回跨 `k=10` 这条线。来源是改写那一步：它调模型，温度 0 也不保证网关每次
返回同一份拆分，改写不同，召回的排名就不同。打分器是纯函数，被测链路不是 —— 这条实测结论记进了
[5 · 6.4](https://tiltwind.github.io/refund-agent/doc/get-start/5-rag-eval.md#64-链路非确定性与门禁容差)。

五次的实测幅度：`@1` ±0.012（1 条），`@3` ±0.010（1 条），`@10` ±0.021（2 条）。`@1` 前四次
纹丝不动，第五次翻了一条 —— 「这一档是稳定的」不能靠四个点下结论，容差要按最坏的那一档定。
门禁容差要覆盖这部分噪声，否则会把改写的抖动读成检索退化。降噪的选项：

| 做法 | 代价 |
|---|---|
| 按 query 缓存改写结果，跟数据集一起版本化 | 与 4.1 缓存拆 claim 同一个思路；改写提示词变了要重建缓存 |
| 门禁 run 固定 `REFUND_AGENT_REWRITE=off` | 测的不再是线上链路，排序质量整体掉一档，基线要重打 |
| 只用 run 级均值做门禁，容差按实测噪声定 | 最省事；五次的幅度已经量出来了，再攒几次才好定线 |

另外记一笔：模型偶尔返回 `intent="law"`，不在
[`rewrite.py`](../../retrieving/pipeline/rewrite.py) 的 `Intent` 字面量里，pydantic 校验失败，
整条 query 降级为原文透传。前四次全量跑批各 0 次，`baseline-4` 出现 1 次（R1-011 那一批）。
它落在改写这一步，正是上面那个噪声源的一部分 —— 而且是幅度最大的一种：整条 query 不改写了。

## 七、两个 LLM 指标读到了什么

`context_recall` 0.915（n=96）、`context_relevance` 0.238（n=92，4 条空证据没有分母）。
两个都只作观察，下面这些结论在 judge 校准之前不采信。

### 7.1 四象限：把「检索失败」和「标注不全」分开

| 象限 | n | 占比 | 判断 | 动哪里 |
|---|---|---|---|---|
| `@3` 判负 · `CR` 低 | 11 | 11% | 真的没召回 | 召回层，先看 `recall@10` 分档 |
| `@3` 判负 · `CR` 高 | 12 | 12% | 召回了等价条款，种子 ID 判负 | 检索没问题，是 `seed_chunk_id` 不全 |
| `@3` 命中 · `CR` 低 | 0 | 0% | 种子块召回了但答案撑不住 | 切片或装配 |
| `@3` 命中 · `CR` 高 | 73 | 76% | 检索没问题 | 答复仍然错的话，问题在生成阶段 |

第二行是这两个指标存在的理由：`@3` 判负的 23 条里，超过一半（12 条，`CR` 全部是 1.0）的上下文
照样撑得住参考答案。只报 Recall 的话，这 12 条和真正没召回的 11 条长得一模一样，按它调参就是
在拟合标注。这 12 条应当回到 [4 · 5.3](https://tiltwind.github.io/refund-agent/doc/get-start/4-rag-dataset.md#53-种子块不等于全部相关块)
说的那件事上：补 `seed_chunk_id`，而不是改重排权重。

第三行是 0，这不是好消息 —— 它更可能说明 judge 判得松（见 7.3），而不是装配一次都没截断过。

### 7.2 `CRel` 的用途是横向对比，不是绝对值

92 条的分布：最低 0.019、中位 0.193、最高 1.0，均值 0.238。低是设计使然：一条 `PolicySection`
是回填后的完整小节，里面混着不相关的句子是父块回填故意带进来的
（[3 · 五](https://tiltwind.github.io/refund-agent/doc/get-start/3-rag-impl.md#五第-4-步--切片-ragchunking)）。

它现在有两个已经兑现的用途：一是 5.2 的兜底判据（语料里没有的问题判出 0.000）；二是配合
`CR` 读 `top_k` 这类参数 —— 调大时 `CR` 上升、`CRel` 下降，两个一起看才知道净赚还是净亏。

而 5.3 说的重复正文它抓不到，那件事仍然归 `duplicate_ratio` 管。

### 7.3 judge 判得偏松，校准要先做

96 条里 85 条 `context_recall` 判满分，`@3` 命中的用例没有一条低于 0.8。判负的 11 条里 4 条是
空证据（分子必然是 0），真正「有上下文但撑不住」的只有 R1-024、R1-046、R1-060、R1-082 等几条。

其中 R1-046 值得单独看：`CR = 0`，两条 claim 说「拆封不支持无理由退货」，而检回的正文写的是
「查验性拆封不影响商品完好、可以退货」—— judge 判的是「上下文里有没有」，判负没错，但这暴露的
是**参考答案与语料相互矛盾**，属于数据集问题，不是检索问题。这类只有逐条判定理由在场才看得出来，
现场在 [`traces/R1-046.md`](./traces/R1-046.md) 的第 6 节。

校准的做法写在 [5 · 7.4](https://tiltwind.github.io/refund-agent/doc/get-start/5-rag-eval.md#74-还没做judge-校准)：
拿人工抽检样本算一致率、假阳假阴分布、同一批判两遍的自一致性。这一轮用的是 `deepseek-v4-flash`，
换模型历史分数就不可比，所以 `config.judge_model` 记在结果文件里。

## 八、开销

| 路径 | 102 条耗时 | 瓶颈 |
|---|---|---|
| 离线 | 75.6s | 检索本身 |
| `--langfuse` | 206~218s | 上报与 dataset run 的编排 |
| `--langfuse --judge` | 2940.1s | judge，占 98% |

`baseline-4` 里检索六步合计只用了 224s，其余 2700 多秒全在每条两次的 judge 调用上。judge 开着
思考模式：拿一条真实的装配产物（104 个内容单元）实测一次 Context Relevance 调用，输出 21168
token，其中 20963 是思考 token —— 99%。

思考是有意留的：DeepSeek 上 thinking 与 `function_calling` 要设的 `tool_choice` 冲突，二选一时
留下了思考（走 `json_mode`），因为判 claim 该让模型多想一步。但这个取舍对两个指标的性价比不同 ——
Context Recall 只判 4~6 条 claim，Context Relevance 要逐个判上百个内容单元，思考量随单元数线性涨，
大头在后者。

跑完这一轮后把思考关了（`REFUND_AGENT_JUDGE_REASONING="none"`）。同一份输入实测 171.2s → 2.2s，
输出 21168 → 187 token。但**分数跟着变**：拿 8 条样本、同一份上下文对比，Context Recall 一致 6/8
（两条变松：0.0→1.0、0.75→1.0），Context Relevance 两套数之间看不出对应关系（0.034→0.793、
0.049→0.659、0.812→0.368）。

所以 `baseline-4` 的两个 LLM 指标与之后关思考跑出来的不可比 —— 结果文件因此加记
`config.judge_reasoning` 与 `config.judge_structured`（`baseline-4` 那份还没有这两个字段，
它是思考开着跑的）。三档 Recall 不受影响，judge 不参与它们的判分。

调参时用离线路径，要留档、要做版本对比时才走 `--langfuse`，出报告时才加 `--judge`。
