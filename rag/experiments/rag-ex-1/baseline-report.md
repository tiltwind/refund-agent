r1 全量基线，只算三档 Recall 与两个辅助数，不含 judge。原始数据在
[`result.json`](./result.json)，跑法见 [README](./README.md)。

```
python rag/experiments/rag-ex-1/run_experiment.py --langfuse --run-name baseline-2
```

102 条、206.3s、`error_rate` 0。分数写回 Langfuse dataset run
`retrieval-cases-r1 / baseline-2`，逐条 `trace_id` 落在结果文件里，六步的中间产物（含装配后的
条款全文）在 trace 上。

被测参数：`refund_policy_chunks` / BGE-M3 / bge-reranker-v2-m3 / `top_k=4` /
`candidate_limit=20` / `rrf_k=20` / `min_score=0.30` / `0.80+0.20` / `budget=3000`。

| 情况 | 条数 | 用例（括号是种子块在候选里的名次） | 改哪里 |
|---|---|---|---|

| 进了候选但排 11~19 名 | 6 | R1-006(13)、R1-023(11)、R1-048(19)、R1-080(11)、R1-081(15)、R1-086(11) | RRF 融合的排序，或 `recall@10` 这个 k 值本身 |

|---|---|---|

## 五、这次跑批暴露的三个链路问题

### 5.1 重排后一条都不剩时，`search_policy` 静默返回空列表

4 条用例（R1-006、R1-026、R1-040、R1-074）拿到了 0 条证据，且不报错。R1-074 在 Langfuse 上
`rag.search_policy` 那棵树：

```
rag.recall     candidates[0] = P10#004:03           ← 种子块排第 1
rag.rerank     passed=0, min_score=0.3, dropped=[全部 20 条]
rag.assemble   sections=[]
```

[`milvus.py`](../../retrieving/milvus.py) 对「一条候选都没有」的口径是显式抛异常，理由写得
很清楚：绝不让 Agent 带着一句「未检索到条款」继续往下判定。但「重排后一条都不剩」走的不是
这条路 —— `assemble([])` 返回 `[]`，工具层拿到空列表，Agent 面对零证据，退回的正是凭记忆
答政策那条路。

召回层明明把正确条款排在第 1，`MIN_SCORE = 0.30` 把它连同其余 19 个候选一起砍掉了。这两件事
（阈值偏高、空结果不报错）要分开处理：前者是调参，后者是口径漏洞。

### 5.2 `unanswerable` 的兜底口径不成立

6 条全部没抛异常，`unanswerable_raised = 0.0`。原因是异常只在候选为空时触发，而召回层对任何
query 都能捞回 20 个候选 —— 问「保价规则」照样返回一堆退货条款。数据集这一类样本
（[4 · 5.4](https://tiltwind.github.io/refund-agent/doc/get-start/4-rag-dataset.md#54-单块答不全的问题)）
想测的「链路不硬凑证据」，当前实现里没有对应行为。

两条路：给链路加一个「最高分低于某个下限即判定无适用条款」的判断，或者把这类样本的判据改成
Context Relevance（检回的东西与问题无关，分数应该趋近 0）。前者动线上行为，后者等 judge 接进来。

### 5.3 重复正文占 20.7%

96 条里 58 条含重复，最高 R1-053 的 0.75 —— 四分之三的证据正文是同一段拼了两遍。这与
[`ex-1` 的人工评估报告](../../../evals/experiments/ex-1/human-eval-report.md)在 Agent 侧读到的
是同一个缺陷（那边测得 29.3%），成因在装配的分组键 `(parent_seq, parent_id, section_path)`：
同一父块的子块 `section_path` 各不相同，同一个 `parent_id` 被登记多次。

`rag.assemble` 的 span 带条款全文，重复的段落在 trace 里直接读得到，不必再靠指标反推。而
`recall@3` 满分的用例里照样有 0.4 以上的重复率 —— ID 级 Recall 对它完全无感，这正是当初把
辅助数一起记下来的理由。

## 六、门禁前要解决的一件事：链路不是确定性的

同一套参数跑了四次（两次离线、两次 dataset run），`recall@1` 纹丝不动，另两档各抖一到两条：

| run | `recall@1` | `recall@3` | `recall@10` | `duplicate_ratio` | `evidence_tokens` | 耗时 |
|---|---|---|---|---|---|---|
| 离线 1 | —（口径修正前） | 0.750 | 0.896 | 0.212 | 1260.9 | 75.2s |
| 离线 2 | 0.637 | 0.750 | 0.896 | 0.208 | 1251.3 | 75.6s |
| `baseline-1` | 0.637 | 0.750 | 0.875 | 0.212 | 1261.4 | 218.2s |
| `baseline-2` | 0.637 | 0.760 | 0.885 | 0.207 | 1267.0 | 206.3s |

翻转集中在 R1-006、R1-023、R1-064、R1-080 这几条 —— 种子块在候选里本来就排 11~13 名，来回
跨 `k=10` 这条线。来源是改写那一步：它调模型，温度 0 也不保证网关每次返回同一份拆分，改写
不同，召回的排名就不同。打分器是纯函数，被测链路不是 —— 这条实测结论记进了
[5 · 6.4](https://tiltwind.github.io/refund-agent/doc/get-start/5-rag-eval.md#64-链路非确定性与门禁容差)。

四次的实测幅度：`@3` ±0.010（1 条），`@10` ±0.021（2 条）。门禁容差要覆盖这部分噪声，否则会把
改写的抖动读成检索退化。降噪的选项：

| 做法 | 代价 |
|---|---|
| 按 query 缓存改写结果，跟数据集一起版本化 | 与 4.1 缓存拆 claim 同一个思路；改写提示词变了要重建缓存 |
| 门禁 run 固定 `REFUND_AGENT_REWRITE=off` | 测的不再是线上链路，排序质量整体掉一档，基线要重打 |
| 只用 run 级均值做门禁，容差按实测噪声定 | 最省事；四次的幅度已经量出来了，再攒几次才好定线 |

另外记一笔：试跑时遇到两次改写降级 —— 模型返回 `intent="law"`，不在
[`rewrite.py`](../../retrieving/pipeline/rewrite.py) 的 `Intent` 字面量里，pydantic 校验失败，
整条 query 降级为原文透传。四次全量跑批各 0 次，属偶发，但它落在改写这一步，正是上面那个
噪声源的一部分。

## 七、两条路径的开销

同样 102 条，离线 75.6s，`--langfuse` 206~218s。差的是上报和 dataset run 的编排开销，不是检索
变慢了 —— `baseline-2` 每条 trace 的 payload 从 5KB 涨到 19KB（补了条款全文），耗时反而比
`baseline-1` 少 12s，可见瓶颈不在 payload 大小。

调参时用离线路径，要留档、要做版本对比时才走 `--langfuse`。
