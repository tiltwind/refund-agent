三、两个 LLM 指标

Context Recall = 被检回上下文支撑的 claim 数 / 参考答案拆出的 claim 总数， claim 跟着样本走（cases.jsonl 的 claims 字段），不在跑批时现拆 —— 分母得在两次 run 之间保持一致，否则涨跌读不出是链路变了还是拆分变了。 Context Relevance = 与 query 相关的内容单元数 / 检回的内容单元总数，内容单元取句子， 表格行整行算一个。两个都判在 PolicySection.text 上，那是真正注入模型上下文的东西。

这两个数现在只记录，不参与 pass / fail。judge 本身还没校准 （与人工标注的一致率、判两遍的自一致性都还没测），而链路自身也有非确定性 —— 两者从跑批结果上 分不开。Context Relevance 的绝对值本来就不该追求高：一条 PolicySection 是回填后的完整小节，里面混着不相关的句子是父块回填故意带进来的。它的用途是横向对比： top_k 调大时 Context Recall 上升、它下降，两个一起看才知道是净赚还是净亏。

四、四个链路问题

MIN_SCORE = 0.3 把召回层排第一的种子块也滤掉了

3 条重排后一条证据都不剩，而它们的 recall@10 全部判正： R1-026（候选第 1）、R1-040（候选第 3）、R1-074（候选第 1）。种子块在召回层排在最前面，重排给出的分低于 0.3，20 条候选连同它一起被砍光，recall@3 与 recall@1 各因此丢 3 条。

rag.recall     candidates[0] = P10#004:03      ← 种子块排第 1
rag.rerank     passed=0, min_score=0.3, dropped=[全部 20 条]
rag.assemble   sections=[]

这是调参：阈值往下调能救回这几条，代价是低分噪声一并进证据。它与第五节那张「候选 → 证据」 表动的是同一组参数，要一起调、一起看。

重排后一条不剩时，search_policy 返回空列表而不抛异常

候选为空时链路是显式抛异常的，重排后为空时不是 —— assemble([]) 返回空列表， 工具层拿到零证据，Agent 退回凭记忆答政策那条路。这次有 4 条走到这里： 上一条那 3 条，加上种子块本就没进候选的 R1-006。

这不是上一条的另一种说法。把 MIN_SCORE 调低只是让这几条不再触发，口径不变： 「一条可用证据都没有」与正常结果在返回值上仍是同一种东西，调用方无从区分。 下面 unanswerable 那 6 条撞的也是这一条。

unanswerable 的兜底口径不成立

6 条全部没抛异常（unanswerable_raised = 0）。异常只在候选为空时触发，而召回层对任何 query 都能捞回 20 条。实际发生的是另一回事：5 条被 MIN_SCORE 全滤成空证据， 剩下 1 条返回了不相关的条款、相关度判出来是 0.000。

也就是说链路对这类问题多半已经「什么都没给」，但给不出与前一个问题的区别 —— 空证据与「语料里没有适用条款」在返回值上是同一个空列表。要么给链路加一个 「最高分低于下限即判无适用条款」的显式结论，要么把这类样本的判据改成 Context Relevance。

重复正文占 20.8%

最高是 R1-053 的 75%。成因在装配的分组键 (parent_seq, parent_id, section_path)：同一父块的子块 section_path 各不相同， 同一个 parent_id 被登记多次。recall@3 满分的用例里照样有 0.4 以上的重复率， ID 级 Recall 对它完全无感。
