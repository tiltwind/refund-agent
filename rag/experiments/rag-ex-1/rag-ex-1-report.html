三、两个 LLM 指标

Context Recall = 被检回上下文支撑的 claim 数 / 参考答案拆出的 claim 总数， claim 跟着样本走（cases.jsonl 的 claims 字段），不在跑批时现拆 —— 分母得在两次 run 之间保持一致，否则涨跌读不出是链路变了还是拆分变了。 Context Relevance = 与 query 相关的内容单元数 / 检回的内容单元总数，内容单元取句子， 表格行整行算一个。两个都判在 PolicySection.text 上，那是真正注入模型上下文的东西。

这两个数现在只记录，不参与 pass / fail。judge 本身还没校准 （与人工标注的一致率、判两遍的自一致性都还没测），而链路自身也有非确定性 —— 两者从跑批结果上 分不开。Context Relevance 的绝对值本来就不该追求高：一条 PolicySection 是回填后的完整小节，里面混着不相关的句子是父块回填故意带进来的。它的用途是横向对比： top_k 调大时 Context Recall 上升、它下降，两个一起看才知道是净赚还是净亏。

四、四个链路问题

空证据现在显式抛异常，代价是三档全记 0

重排后一条证据都不剩时，search_policy 抛 NoEvidenceError，不再把空列表 交给 Agent —— 调用方能区分「没有适用条款」与正常结果了。answerable 里有 5 条走到这条路：R1-006、R1-026、R1-040、R1-074、R1-080。

判分口径跟着定成：这几条留在 Recall 分母里、三档一律判负，否则新增的兜底会让均值看起来变好。 代价是 recall@10 对它们不再是召回层的读数 —— 异常在装配前抛出， 跑批拿不到 trace，种子块在候选里排第几没有记录。第五节那张表因此单列了一类。

rag.recall     candidates = 20 条
rag.rerank     passed=0, min_score=0.3, dropped=[全部 20 条]
rag.assemble   → NoEvidenceError

MIN_SCORE = 0.3 是这 5 条的直接原因

候选层每次都能捞回 20 条，被砍光发生在重排：全部候选的相关度都低于 0.3。阈值往下调能救回它们，代价是低分噪声一并进证据 —— 它与第五节那张 「候选 → 证据」表动的是同一组参数，要一起调、一起看。

要判断这几条到底是「重排压低了本该命中的块」还是「召回层本来就没捞到」，得让异常路径也把 trace 带出来。现在只能从 现场记录 逐条看。

unanswerable 的兜底口径已经成立

6 条全部按口径抛异常（unanswerable_raised = 1.000）。 走的正是上面那条路：语料里没有适用条款时，召回层照样捞回 20 条， 但没有一条过得了 0.3。

口径成立不等于判据可靠 —— 现在「没有适用条款」与「有条款但重排分偏低」触发的是同一个异常， 两者只有靠阈值分开。这一档的把握程度取决于 MIN_SCORE 定得准不准， 校准要跟 Context Relevance 一起做。

重复正文占 19.8%

最高是 R1-053 的 75%。这是一个内容重复信号， 不证明重复一定由装配造成：不同父块、不同文档本身也可能含相同的标准表述。 recall@3 满分的用例里照样有 0.4 以上的重复率，ID 级 Recall 对它完全无感 —— 归因要对着 trace 和装配测试看。
