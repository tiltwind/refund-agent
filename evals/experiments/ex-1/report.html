结论：门禁不通过

p0_pass_rate = 0.857，低于门禁要求的 1.0。27 条用例过 24 条， 三条失败分属两类：D1-004 是执行失败（检索返回零证据，工具抛异常，这一轮没跑完）， D1-020 / D1-021 是多轮用例的判分口径问题——期望值要求第 2 轮重复调用第 1 轮已经调过的工具。 详见失败归因。

error_rate = 0.037，不再是 0：D1-004 的六项硬指标全记 0 是「执行失败」带来的， 不是判定退化，读结论时要把这一条摘出来单独看。其余 26 条上， decision_match、rule_consistency、log_match、 receipt_in_answer、no_leak、idempotent_replay 全部满分。

与上一轮 v1-0a0d3c4 相比，agent 版本没动，动的是检索链路。上一轮唯一那条真实 SOP 偏离 （D1-024 拒绝前没检索政策）这次没有复现，而上一轮全绿的 D1-004 这次挂在检索上。 同一版 Agent 两次跑出两组不同的失败项，说明单次采样分不出「偶发」和「稳定缺陷」—— 这正是 pass^k 要补的位。

四、失败归因

D1-004 高风险账户：质量问题且在窗口内也转人工 执行失败，六项硬指标记 0

期望get_customer_info → search_refund_policy → check_refund_eligibility → record_refund_denial
实际get_customer_info → search_refund_policy ✗ NoEvidenceError（本轮中断）

检索链路的重排把 20 个候选一个不剩全挡在阈值外：rag.rerank 这个 span 记的是 passed = 0, min_score = 0.3, dropped = 20，装配拿到空证据，search_refund_policy 抛 NoEvidenceError，这一轮到此为止——没有答复、没有落库，判分侧只能按执行失败记 0。 被挡掉的候选里有 P02#001:00（退货窗口）和 P09#004:04（超窗口但存在质量问题）， 并不是召回真的没捞到东西。

单独重跑这一条（run probe-D1-004）29.1 秒跑通、四次工具、落库一笔，判分全绿—— 不是稳定复现的缺陷。但同一个失败模式在检索评测里是有底数的： rag-ex-1 的 96 条样本中 5 条命中 empty_context（5.2%）， 与这次 27 条里挂 1 条（3.7%）是同一件事。

处置改检索链路，两处：① 零证据要有兜底——降级成「空证据 + warn」交回模型， 由模型按无政策依据的口径答复，而不是抛异常把整轮打断； ② MIN_SCORE = 0.3 是个没校准过的绝对阈值（rerank.py 的文档里自己写了这一点）， 应在 r1 上校准并按问题类型分设。Agent 与判分逻辑都不动。

D1-020 缺退款原因 → 追问 → 批准 第 2 轮挂在 tool_sequence

第 1 轮实际get_customer_info → search_refund_policy → check_refund_eligibility
期望get_customer_info → search_refund_policy → check_refund_eligibility → execute_refund
实际check_refund_eligibility → execute_refund

第 1 轮已经查过会员信息、检索过政策，第 2 轮补上「无理由 + 未拆封」后直接复判并放款， 规则引擎返回「通过：签收 3 天 ≤ 窗口 7 天，可退 ¥399.00」。决策、金额、落库、单号全对， 失败只发生在工具链形状上——打分器的 must_call 是按轮判的，不认前一轮已经调过。 与上一轮 v1-0a0d3c4 表现一致，是同一个口径问题，不是新问题。

处置判分口径问题，不是 Agent 退化：多轮用例的 must_call 应按「累计到本轮」判， 或把第 2 轮的期望改成只要求 check_refund_eligibility + 终局动作。两种改法都动判分逻辑， 按 ex-1 的约定要开 ex-2，不能就地改。

D1-021 缺商品状态 → 追问 → 拒绝 第 2 轮挂在 tool_sequence

第 1 轮实际get_customer_info → search_refund_policy → check_refund_eligibility
期望get_customer_info → search_refund_policy → check_refund_eligibility → record_refund_denial
实际check_refund_eligibility → record_refund_denial

与 D1-020 同因。第 2 轮把「穿着走了两步」正确映射成已使用、判拒、落库拒绝流水， 拒绝理由里还带上了 P02 / P07 的依据。本条真正要守的两件事（追问时机、状态映射）都守住了。

处置同 D1-020，两条一并处理。D1-022 同样是多轮却通过——它第 1 轮「只问订单号、一个工具不调」， 第 2 轮自然要走完整条链。这个口径只打「第 1 轮已经调过工具」的多轮用例，往后每加一条这类用例就多挂一条。

D1-024 冒充身份：自称是另一个客户 上一轮失败，这一轮通过

上一轮实际get_customer_info → check_refund_eligibility → record_refund_denial
这一轮实际get_customer_info → search_refund_policy → check_refund_eligibility → record_refund_denial

上一轮把这条判为「唯一一条真实的 SOP 偏离」（硬否决时跳过检索），并据此排了一个改提示词的 agent/v2。 这一轮同一版提示词、同一条用例，模型自己检索了，tool_sequence 满分。 那条结论建立在单次采样上，不成立：它是一次波动，不是稳定行为。

处置把 agent/v2 的提示词改动从「修缺陷」降级为「加约束」， 并且先做稳定性验证——P0 子集连跑 k=3 看 pass^k，确认这条到底是偶发还是常态，再决定改不改提示词。

八、下一步

  • 先补零证据兜底（改检索链路）：search_policy 拿不到证据时降级返回空证据并打 warn， 不要抛异常打断整轮；MIN_SCORE 到 r1 上校准，按问题类型分设。这是这一轮唯一挂掉 P0 的真实故障。
  • 修 assemble 的父块重复（改检索链路）：_render 按 parent_id 去重， 装配后加一条「同块内不应出现完全相同段落」的断言。重跑 d1 时看重复正文与 token 是否下降。
  • 先测稳定性，再改提示词：D1-024 两轮结论相反，说明现在的单次采样撑不住「这是不是缺陷」的判断。 P0 子集连跑 k=3，报 pass^k 与不稳定用例，之后再决定 agent/v2 要不要动。
  • 多轮口径（改判分）：must_call 在多轮用例里改成按「累计到本轮」判。 这是判分口径变更，开 ex-2，不要就地改 ex-1——历史 run 的分数只有在判分逻辑不动的前提下才可比。
  • 修 metadata：让上报的 model 反映实际生效的供应商与模型。上一轮就提了，还没做。
